# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

1. Доступ к секретам:
   - Кто: `kubernetes-admin`
   - Где: namespace `kube-system`, секрет `bootstrap-token-0ajev6`
   - Почему подозрительно: Администратор читает загрузочный токен (`bootstrap-token`). Такие токены позволяют новым узлам присоединяться к кластеру. Чтение без явной операционной необходимости может быть попыткой кражи чувствительных данных для дальнейшей компрометации.

2. Привилегированные поды:
   - Кто: `minikube-user`
   - Комментарий: Дважды создавался под `privileged-pod` (auditID: `560051b5…` и `f88a85f0…`) с `securityContext.privileged: true`. Контейнер в привилегированном режиме получает доступ ко всем устройствам и ресурсам хостовой машины, что может быть использовано для эскалации привилегий или побега из контейнера.

3. Использование kubectl exec в чужом поде:
   - Не обнаружено в имеющемся аудит-логе. Политика аудита, настроенная в `audit-policy.yaml`, не включала подресурс `exec` для логирования (правило для `pods` не охватывает `subresources`). Следовательно, событие не было записано, хотя команда выполнялась.

4. Создание RoleBinding с правами cluster-admin:
   - Не обнаружено. Аудит-лог не содержит событий создания `rolebindings` с ролью `cluster-admin`. Это может означать, что либо политика аудита не захватила запрос (правило `RequestResponse` для `rolebindings` срабатывает, но если запрос был к другой API-группе или не попал по времени), либо событие не было сгенерировано. Требуется дополнительная проверка.

5. Удаление audit-policy.yaml:
   - Не обнаружено. В логе отсутствуют события удаления ресурса `policies.audit.k8s.io` или запросы с `audit-policy` в URI. Вероятно, политика аудита не отслеживает API-группу `audit.k8s.io` (второе правило уровня `Metadata` было ограничено ресурсами `["pods", "secrets", …]` и не включало `policies`). Поэтому попытка удаления не записалась.

## Вывод

Аудит зафиксировал две явные подозрительные активности: чтение администратором загрузочного токена и запуск привилегированного контейнера. Остальные действия симуляции (`exec`, `RoleBinding`, удаление политики) не отразились в логе из-за неполной политики аудита.
Это демонстрирует важность тщательной настройки аудита: политика должна охватывать все критичные ресурсы и подресурсы (например, `pods/exec`, `rolebindings` в `rbac.authorization.k8s.io`, `policies.audit.k8s.io`).
Текущая конфигурация RBAC позволяет пользователю `minikube-user` создавать привилегированные поды, а `kubernetes-admin` имеет неограниченный доступ, включая чтение секретов в системных неймспейсах. Рекомендуется:
- ограничить использование привилегированных контейнеров с помощью Pod Security Standards,
- пересмотреть роли и исключить ненужные права,
- расширить аудит-политику для регистрации всех подозрительных операций.
